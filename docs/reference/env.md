Generated by `bun run docs:gen` from `apps/api/src/lib/env.ts` and the code under `apps/` and `bundled-apps/`. Do not edit.

Every variable the server reads at boot is a key of its environment schema. A missing required key, or a value of the wrong type, stops the process (exit 2 under the CLI).

| `REQUEST_TIMEOUT_MS` | `number` | `30000` | no | Global per-request timeout (ms) for /api/* except the long-lived agent-chat stream. 30s is the production ceiling; the chaos profile raises it (a CPU-contended box can make an approved gated write — out-of-process sandbox + a live upstream API call — exceed 30s, which would 504 a correct-but-slow write). | `DB_CONNECT_TIMEOUT` | `number` | `10` | no | postgres.js connect_timeout (seconds). 10s is the production default; the chaos profile raises it so a connect under heavy CPU contention waits rather than failing CONNECT_TIMEOUT. |
| `DB_ACQUIRE_TIMEOUT_MS` | `number` | `25000` | no | Max time (ms) to WAIT FOR A FREE POOL SLOT before a privileged DB transaction fails fast. postgres.js (3.4.9) queues pool-slot acquisition with NO timeout (connect_timeout only bounds NEW-socket establishment, not waiting for an in-use connection to free). A gated approved handler runs inside an RLS transaction (connection A) and then nests a privileged token lookup (connection B) -- so each in-flight gated Shopify handler holds 2 slots; concurrent handlers can exhaust the pool and the nested acquisition then waits UNBOUNDED, hitting the 300s sandbox ceiling ("App execution timed out"). Bounding the wait converts that hang into a fast, retryable failure (chaos retries on a fresh world). 25s keeps it well under the 300s sandbox ceiling while tolerating brief CPU-contended bursts. 0 disables the bound (legacy unbounded behaviour). |
| `DB_STATEMENT_TIMEOUT_MS` | `number` | `10000` | no | Per-statement ceiling (ms) applied INSIDE withRlsContext's transaction via `SET LOCAL statement_timeout` -- the main-pool analogue of DB_ACQUIRE_TIMEOUT_MS. U4.16 root cause: a sandboxed tool handler (e.g. tickets:search at 4,730-ticket corpus scale) can issue a slow query that outlives executeInSandbox's own wall-clock timeout. executeInSandbox gives up and rejects, but without a server-side statement_timeout the ORIGINAL query keeps running on that connection's socket -- postgres.js can only send ROLLBACK after the in-flight statement finishes, so the connection is NOT returned to the pool until then (in the worst case, a lock wait, never). Enough concurrent timeouts exhaust DB_POOL_MAX and wedge every tool/job that needs a DB connection (observed live: "privileged db pool-slot acquire timed out -- pool exhausted" cascading across slaCheck/imap-incremental-sync/followupCheck/etc, cleared only by a full `compose restart app`). Killing the statement server-side lets the transaction actually roll back and the connection return to the pool -- the real "reclaim". 10s matches the existing apps/database read-transport's DEFAULT_STATEMENT_TIMEOUT_MS precedent; comfortably above the 5s production sandbox ceiling (so a normal timeout still surfaces as "App execution timed out" first) but far below the acquire-timeout, so a genuinely stuck query is killed well before it can exhaust the pool. 0 disables (legacy unbounded behaviour). |
| `DB_RLS_JIT_ENABLED` | `boolean` | `false` | no | U4.16 finding 2 root cause (measured, not guessed): withRlsContext's RLS policies (app_tickets.tickets/messages -- jsonb dimension checks + string_to_array/unnest scope checks, evaluated per-row) compound with tickets:search's free-text ILIKE/EXISTS predicates into a query plan large enough that Postgres's JIT compiler engages -- and JIT COMPILE TIME dominates wall-clock, not row processing. Measured directly against the U4.16 realistic-scale fixture (5,000 tickets / 30,000 messages, RLS role active): the identical plan took 1,478ms with JIT on vs 10ms with JIT off -- a ~148x difference, entirely compile overhead (EXPLAIN's own JIT block reported ~1,450ms of that as Generation/Inlining/Optimization/Emission). This fires on EVERY query inside the RLS transaction, and tickets:search issues up to 3 per call (the always-on COUNT(*), the precise AND page, and the OR recall-widening fallback) -- so a multi-term query could pay the ~1.5s JIT tax three times, well past the 5s production sandbox ceiling once real load/concurrency is added. JIT is tuned for large analytical scans; these are short, bounded (LIMIT ≤100), latency- sensitive OLTP reads -- JIT is a pure loss here, not a tradeoff. Default off; set to true to restore Postgres's default per-connection jit GUC (whatever postgresql.conf configures) if a future workload benefits. |
