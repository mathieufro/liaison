## How long it takes

Measured on a live install with a coding agent running the AGENT steps: about 9 minutes for a trial on your own machine (your knowledge and agents, no mailbox yet, so nobody else can sign in); about 15 minutes for the basic onboarding on a server (the mail sender, Google sign-in, your team, the support inbox and your company knowledge); up to about 2 hours of your own time for a full onboarding on a server with every connector. The table splits those totals: your own time for each part, in the provider's console with its exact instructions in hand (the basic parts add up to 14 to 30 min, the full onboarding to 60 to 114 min; the parts marked *on top* are outside it: a system of your own, or an alternative to another part); each HUMAN step below says its own time, and `liaison setup state` adds up the parts that are left. The waits are the provider's, not yours, are never in a total, and some take days.

## The server

### Domain and https

Variables: `BASE_URL`, `ALLOWED_ORIGINS`.

1. **HUMAN** (2 min) Choose the address people will use, for example liaison.your-company.com. At your DNS provider, add an A record for that name pointing to this server's public IP address (or a CNAME to its host name).
2. **AGENT** Set BASE_URL and ALLOWED_ORIGINS in deploy/.env to that https address, without a trailing slash.
   `BASE_URL=https://liaison.example.com`
   `ALLOWED_ORIGINS=https://liaison.example.com`
3. **AGENT** Put https in front of the app: Caddy on the server (automatic certificates) or a Cloudflare Tunnel, as in docs/runbooks/production-bootstrap.md, section TLS + DNS.

Verify: curl -fsS https://liaison.example.com/healthz answers ok from another machine.

### Outbound mail and the sender domain

Variables: `RESEND_API_KEY`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_SECURE`, `EMAIL_FROM`, `SYSTEM_EMAIL_FROM`.

1. **HUMAN** (2 min) Pick a mail provider. With Resend: sign up, open Domains, click Add Domain and enter the domain you send from (a subdomain such as mail.your-company.com is fine). Any SMTP provider (Postmark, Mailgun, Amazon SES, Brevo, your own server) works the same way through its domain page.
   Open: <https://resend.com/domains>
2. **HUMAN** (2 min) At your DNS provider, create exactly the records the mail provider shows for <your-domain>: the SPF (TXT) record and the DKIM records it generates. Then add a DMARC record (TXT on _dmarc.<your-domain>). Back in the provider, click Verify and wait until the domain shows Verified.
   `_dmarc.<your-domain>  TXT  "v=DMARC1; p=none; rua=mailto:postmaster@<your-domain>"`
3. **HUMAN** (1 min) Create a sending API key (Resend: API Keys, Create API Key, permission Sending access) or the SMTP user and password, and put it in the secrets file, never in the chat.
   Open: <https://resend.com/api-keys>
4. **AGENT** Set the transport and the sender in deploy/.env: RESEND_API_KEY (or SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASS; port 465 also needs SMTP_SECURE=true), and EMAIL_FROM on that domain. Remove LIAISON_CONSOLE_EMAIL_BODIES. Restart the app so it reads deploy/.env: `docker compose -f deploy/docker-compose.yml up -d app`.
   `EMAIL_FROM=Your Company <noreply@<your-domain>>`

Verify: Sign in at BASE_URL with the owner's address: the code arrives in the inbox (not spam) within a minute, and the message headers show spf=pass and dkim=pass.

### Model keys

Variables: `OPENROUTER_API_KEY`, `LIAISON_ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GOOGLE_API_KEY`, `MISTRAL_API_KEY`.

1. **HUMAN** (1 min) Create an OpenRouter key (one key reaches every model): open the keys page, click Create Key, name it, and put it in the secrets file.
   Open: <https://openrouter.ai/settings/keys>
2. **AGENT** Give it to the workspace in the config (`byok: { openrouter: { apiKey: "${OPENROUTER_API_KEY}" } }`) and run `liaison config apply`. Only a server shared by several workspaces sets OPENROUTER_API_KEY in deploy/.env as the fallback.

Verify: The `config apply` report shows byok.openrouter validated, and `liaison agent ask` gets an answer.

### Backups

1. **AGENT** Add a nightly cron line on the host that runs deploy/backup.sh and keeps two weeks, then copy each archive off the machine (docs/admin/backups.md).
   `15 3 * * * cd /opt/liaison && ./deploy/backup.sh --keep 14 >>/var/log/liaison-backup.log 2>&1`
2. **HUMAN** (1 min) Keep a copy of deploy/.env (the keys) somewhere safe outside the server: without ENCRYPTION_KEY a backup cannot be read.

Verify: Run ./deploy/backup.sh once by hand: it prints the archive path and exits 0.

### Sign in with Google (optional)

Variables: `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`.

1. **HUMAN** (1 min) If the project has no consent screen yet, Google asks for one first: on Branding, an app name and a support email. Then open Audience and say what User type it shows (a screenshot of the page is fine): Internal when the project belongs to your company's Google Workspace and everyone who signs in has an address there (no Google review, nothing to mark Trusted); External only otherwise. Sign-in uses only openid, email and profile, which need no Google review.
   Open: <https://console.cloud.google.com/auth/audience>
2. **HUMAN** (2 min) Open Clients, click Create client, choose Web application, name it Liaison. Under Authorized redirect URIs click Add URI twice and paste both values below: one client serves Sign in with Google and every Google connection (Gmail, Calendar, Drive, Ads), since Google asks for each permission when an account connects, not per client. Click Create, then Download JSON and give the agent the downloaded file's path.
   Open: <https://console.cloud.google.com/auth/clients>
   `https://liaison.example.com/api/auth/oauth/callback`
   `https://liaison.example.com/api/connections/callback`
3. **AGENT** Read client_id and client_secret from the downloaded JSON (check its redirect_uris list both values), write them to the secrets file without printing them, then delete the download. Set GOOGLE_OAUTH_CLIENT_ID and GOOGLE_OAUTH_CLIENT_SECRET in deploy/.env. The same pair is the workspace's Google client: give it in the config (a google: block on the mailbox or inbox), or as GMAIL_OAUTH_* on a server shared by several workspaces. When the audience is Internal, also set GOOGLE_OAUTH_INTERNAL_DOMAINS to the Workspace domain. Restart the app so it reads deploy/.env: `docker compose -f deploy/docker-compose.yml up -d app`.

Verify: The sign-in page shows Continue with Google, and an invited person signs in with it.

### OAuth clients the server provides to every workspace (optional)

Variables: `GMAIL_OAUTH_CLIENT_ID`, `GMAIL_OAUTH_CLIENT_SECRET`, `GOOGLE_DRIVE_OAUTH_CLIENT_ID`, `GOOGLE_DRIVE_OAUTH_CLIENT_SECRET`, `GOOGLE_MARKETING_OAUTH_CLIENT_ID`, `GOOGLE_MARKETING_OAUTH_CLIENT_SECRET`, `SHOPIFY_APP_CLIENT_ID`, `SHOPIFY_APP_CLIENT_SECRET`, `GOOGLE_OAUTH_RESTRICTED_SCOPES_VERIFIED`, `GOOGLE_OAUTH_INTERNAL_DOMAINS`, `GMAIL_PUBSUB_TOPIC`.

1. **AGENT** Print the values each client needs: `liaison guide google` (redirect URI, scopes, APIs, Gmail push topic) and `liaison guide shopify` (app URL, redirect URL, scopes, API version). The redirect URI of every one of them is the value below.
   `https://liaison.example.com/api/connections/callback`
2. **HUMAN** (10 min) Create each client as those guides say (Google: the Clients page below; Shopify: https://dev.shopify.com/dashboard), and put each ID and secret pair in the secrets file.
   Open: <https://console.cloud.google.com/auth/clients>
3. **AGENT** Set the pairs in deploy/.env (GMAIL_OAUTH_*, GOOGLE_DRIVE_OAUTH_*, GOOGLE_MARKETING_OAUTH_*, SHOPIFY_APP_*). GMAIL_PUBSUB_TOPIC is the topic Gmail push publishes to (the topic grants gmail-api-push@system.gserviceaccount.com Pub/Sub Publisher). Set GOOGLE_OAUTH_RESTRICTED_SCOPES_VERIFIED=true only once Google has verified the Google clients for restricted scopes. When the clients' audience is Internal (their project belongs to your Google Workspace), set GOOGLE_OAUTH_INTERNAL_DOMAINS to that Workspace's domain: its addresses then connect with no Trusted mark. One Web client may serve all the Google pairs and Sign in with Google. Restart the app so it reads deploy/.env: `docker compose -f deploy/docker-compose.yml up -d app`.

Verify: `liaison setup state` shows those connections with client `instance`.

### ads

#### ads/google: Google Ads account

#### ads/google-config: Google Ads API settings

Credentials, optional. Steps on your server: `liaison guide ads/google-config`.

Optional, advanced: set this up only if you want the agent to read and manage your Google Ads. Enter the manager (login) customer id, the ad account's customer id and, if you sell through Google Shopping, the Merchant Center account id. No developer token is needed. Customer ids are digits only, no dashes.

1. **HUMAN** (3 min) Google Ads needs no developer token any more: Google retired them on 2026-09-09 (a token left in an old config is ignored, never sent), and API access now belongs to the Google Cloud project of the OAuth client the google connection uses. In that project, enable the Google Ads API (https://console.cloud.google.com/flows/enableapi?apiid=googleads.googleapis.com), then open https://console.cloud.google.com/google/ads-apis/overview, expand **Upgrade access level** and click **Apply for access** to move from Test to **Explorer** (production accounts, 2,880 operations a day, reviewed by Google automatically). Explorer covers every Ads tool here; Basic access (it needs brand verification) is not needed. Do not use the API Center's "Apply for Basic Access" link in Google Ads: it now opens the App Conversion Tracking and Remarketing form, which grants no Google Ads API access.
   Open: <https://console.cloud.google.com/google/ads-apis/overview>
2. **HUMAN** (1 min) Find out whether you sign in to a manager account: open https://ads.google.com/aw/accounts. A manager account has **Accounts** in the left menu and **Manager account settings** under **Admin**; the number at the top left (for example 123-456-7890) is the manager's id: enter it as **loginCustomerId**. No **Accounts** menu means a plain ad account: enter its own id (top left) as both **loginCustomerId** and **customerId**.
   Open: <https://ads.google.com/aw/accounts>
3. **HUMAN** (2 min) In a manager account, the ad account's id is in **Accounts** > **Performance** (https://ads.google.com/aw/accounts), **Account** column, on the row whose **Direct manager** reads **(This manager)**: enter it as **customerId**. One id at a time, digits only (dashes are removed).
   Open: <https://ads.google.com/aw/accounts>
4. **HUMAN** (1 min) Unsure which number is which? Take a screenshot of https://ads.google.com/aw/accounts and share it: the ids are read from it and confirmed back to you before they are saved.
   Open: <https://ads.google.com/aw/accounts>
5. **HUMAN** (2 min) Merchant Center is optional: first answer "Do you sell products through Google Shopping?". Only if yes, open https://merchants.google.com and copy the account id shown at the top right into **merchantId**; otherwise leave it empty.
   Open: <https://merchants.google.com>
6. **AGENT** The owner pastes the secret values into deploy/.setup-secrets.env (never the chat); put the values in the config: an `apps` entry { name: ads, connection: { name: google-config, credentials: { loginCustomerId, customerId, merchantId (optional), developerToken (secret, optional) } } }, secrets as ${ENV} references to the secrets file, then run `liaison config apply` and `liaison config verify --app ads`.

Credentials. Steps on your server: `liaison guide ads/meta`.

Create a System User in Meta Business Manager, grant it Admin access to your ad account, generate a non-expiring token with ads_management + ads_read + pages_show_list permissions, then paste the token and your ad account id (act_XXXXXXXXX) below.

### api-connector

#### api-connector/api: API connection

Credentials. Steps on your server: `liaison guide api-connector/api`.

Each API connection is an adapter document (the API's base URL, auth type and named operations) plus the credentials its auth type needs. Ask the agent to connect your CRM or ERP: it reads the vendor's API docs, drafts the adapter, asks you to approve the save and to enter the credentials, then tests it. You can also upload an adapter yourself.

1. **AGENT** Ask the agent to connect the system ("connect our CRM, its API docs are at ..."), or write the adapter yourself and upload it under a short slug (for example `crm` or `erp`) in Settings > Connectors > API connector, or with `liaison config apply`.
2. **HUMAN** (1 min) Approve the adapter save: the card shows the API's address, auth type and operations, and warns when the change deletes stored credentials.
3. **HUMAN** (2 min) Enter the credentials the adapter's auth type asks for in the secure form; they are encrypted and never leave the server.
4. **AGENT** Run a read operation (the agent's test, or the Test panel) to confirm the connection answers. History restores an earlier version of the adapter.
5. **AGENT** The owner pastes the secret values into deploy/.setup-secrets.env (never the chat); put the values in the config: an `apps` entry { name: api-connector, connection: { name: api, credentials: { apiKey (secret, optional), token (secret, optional), username (optional), password (secret, optional), clientId (optional), clientSecret (secret, optional) } } }, secrets as ${ENV} references to the secrets file, then run `liaison config apply` and `liaison config verify --app api-connector`.

Provider docs: <docs/api-connector.md>

### calls

#### calls/transcript-source: Transcript webhook

Credentials, optional. Steps on your server: `liaison guide calls/transcript-source`.

Connecting mints the webhook signing secret. Calls never calls out to your transcript source — the connection exists so the kernel generates and stores the HMAC secret your adapter must sign deliveries with.

1. **HUMAN** (1 min) Enter any label describing your transcript source (e.g. `meet-bot-prod`) and connect — the kernel mints a random signing secret on first connect and reuses it afterwards.
2. **AGENT** Read the signing secret with the `calls__webhook_info` tool (admin scope required).
3. **HUMAN** (10 min) Configure your transcript adapter to POST segment/summary JSON to this Liaison instance's `segment` webhook endpoint for the calls app, signing the raw request body with HMAC-SHA256 (base64) under that secret in the `x-calls-signature` header.
4. **HUMAN** Optionally send a unique `x-calls-delivery-id` header per delivery for exact-retry deduplication.
5. **HUMAN** Include a fresh `ts` (ISO-8601 or epoch ms) in every payload — it is covered by the signature and deliveries whose signed `ts` is older (or further in the future) than the freshness window are rejected (default 10 minutes; override via the `callsWebhookTtlSeconds` config key).
6. **HUMAN** This server receives the app's `segment` webhook at https://liaison.example.com/webhooks/<org-id>/calls/segment (the steps above say who registers it).
7. **AGENT** The owner pastes the secret values into deploy/.setup-secrets.env (never the chat); put the values in the config: an `apps` entry { name: calls, connection: { name: transcript-source, credentials: { label } } }, secrets as ${ENV} references to the secrets file, then run `liaison config apply` and `liaison config verify --app calls`.

### database

#### database/database: Operational database

Credentials. Steps on your server: `liaison guide database/database`.

Connect either a direct Postgres DSN (same machine/network, or a hardened public endpoint) OR a liaison-db-gate URL+token (recommended for cross-network / grumpy-devops setups). Exactly one mode — never both.

1. **AGENT** Rung 0/1 (same machine or private network): mint a read-only role with `scripts/db-readonly-role.ts --create` and paste its DSN into connectionString.
2. **AGENT** Rung 2 (db-gate, recommended for anything crossing an untrusted network): stand up the liaison/db-gate sidecar next to your database with a catalog.yaml and a minted bearer token, then paste its URL into gateUrl and the token into gateToken.
3. **AGENT** Rung 3 (public Postgres endpoint): connectionString with TLS required — the connector refuses plaintext to any non-local resolved IP.
4. **AGENT** After connecting, db_probe runs automatically and reports any write/EXECUTE grants beyond the read-only allow-list — review its warnings before relying on this connection.
5. **AGENT** The owner pastes the secret values into deploy/.setup-secrets.env (never the chat); put the values in the config: an `apps` entry { name: database, connection: { name: database, credentials: { connectionString (secret, optional), gateUrl (optional), gateToken (secret, optional) } } }, secrets as ${ENV} references to the secrets file, then run `liaison config apply` and `liaison config verify --app database`.

### monitoring

#### monitoring/alert-source: Alert webhook

Credentials, optional. Steps on your server: `liaison guide monitoring/alert-source`.

Connecting mints the webhook signing secret. Monitoring never calls out to your alerting system — the connection exists so the kernel generates and stores the HMAC secret your alert source must sign deliveries with.

1. **HUMAN** (1 min) Enter any label describing your alert source (e.g. `grafana-prod`) and connect — the kernel mints a random signing secret on first connect and reuses it afterwards.
2. **AGENT** Read the signing secret with the `monitoring__webhook_info` tool (admin scope required).
3. **HUMAN** (10 min) Configure your alerting system to POST alert JSON to this Liaison instance's `alert` webhook endpoint for the monitoring app, signing the raw request body with HMAC-SHA256 (base64) under that secret in the `x-monitoring-signature` header.
4. **HUMAN** Optionally send a unique `x-monitoring-delivery-id` header per delivery for exact-retry deduplication.
5. **HUMAN** Include a fresh `ts` (ISO-8601 or epoch ms) in every payload — it is covered by the signature and deliveries whose signed `ts` is older (or further in the future) than the freshness window are rejected (default 10 minutes; override via the `monitoringAlertTtlSeconds` config key).
6. **HUMAN** (2 min) To clear an alert from the source, POST the same signed envelope shape with `status: "resolved"` (or `event: "resolve"`), the alert's `source`, `dedupKey` and a fresh `ts`; `severity` and `title` are optional. The live incident is resolved automatically (note `cleared by <source> at <ts>`); with no live incident nothing is created, and a resolve older than the latest alert is ignored as stale.
7. **HUMAN** This server receives the app's `alert` webhook at https://liaison.example.com/webhooks/<org-id>/monitoring/alert (the steps above say who registers it).
8. **AGENT** The owner pastes the secret values into deploy/.setup-secrets.env (never the chat); put the values in the config: an `apps` entry { name: monitoring, connection: { name: alert-source, credentials: { label } } }, secrets as ${ENV} references to the secrets file, then run `liaison config apply` and `liaison config verify --app monitoring`.
